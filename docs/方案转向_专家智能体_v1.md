## 1. 关键发现：平台已经解决了最难的两件事

### 1.1 专家包可以内嵌 Skills

专家包的标准结构（实证自本机 `workspace-builder` 专家）：

```
my-expert/
  .codebuddy-plugin/plugin.json     # 展示字段、类型、分类、推荐提示词
  agents/<agentName>.md             # 角色定义、能力、工作流程、输出规范
  avatars/expert.png                # 头像
  skills/                           # ★ 可内嵌多个 Skill
    <skill-name>/
      SKILL.md                      # 指令本体
      references/                   # 参考资料（API 文档、字段定义、模板）
      scripts/                      # 可执行脚本
      templates/                    # 输出模板
  bin/                              # 通用 CLI 工具
```

**结论：之前设计的 11 个 skill，可以直接落成专家包内的 11 个 SKILL.md。**

### 1.2 平台内置「资料库」能力，提供在线存储与页面部署

`workspace-builder` 专家的做法（值得直接照抄）：

1. 任务开始前先加载内置 skill `library`（资料库）
2. 加载成功 → 用它的三项能力：
   - **在线 page / 网页发布** → 把 HTML 发布为公网可访问页面，**直接得到在线链接**
   - **数据表** → 在线结构化存储 + 跨设备双向同步
   - **网盘** → 存储图片等资源
3. 加载失败 → 退回本地 HTML + localStorage

**结论：之前花大量篇幅讨论的部署方案（Vercel / Cloudflare / 国内云厂商 / ICP 备案），全部作废。** 在线链接由平台提供。

## 2. 两种形态对比

| | Web Demo（原方案） | **专家智能体（新方案）** |
|---|---|---|
| 需要写的代码 | Next.js 全栈 + API + 会话管理 + Agent 循环 | 专家包（Markdown + 少量脚本） |
| 对话 UI | 自己实现 | **平台原生，即 Codex 风格** |
| Agent 与工具调度 | 自己实现 | **平台原生** |
| 会话管理 | 自己实现 | **平台原生** |
| 部署 | 自己做（且有备案/可访问性风险） | **用资料库，零部署** |
| 数据持久化 | 自己建数据库 | **用资料库数据表** |
| 对新手友好度 | 低 | **高** |
| AI 工具使用得分 | 中 | **高（专家+Skills+资料库+自动化）** |
| 风险 | 开发量与部署 | 依赖平台能力（需先验证） |

**决策：采用专家智能体的形态。**

## 3. 新架构

```
用户 / 评委 在 LearnBuddy 里对话
        ↓
专家智能体（学术导航）
        ↓ 调用
Skills 工具箱（11 个，统一契约）
        ↓ 读写
资料库（数据表存储 · 在线页面部署 · 跨设备同步）
        ↓
交付：在线链接 · 源码仓库（专家包）· 对话记录
```

### 3.1 专家类型选择：建议 Agent 型

平台支持两种：`agent`（单角色）/ `team`（多角色协作）。

**建议 `agent` 型**，理由：

- 产品的交互范式是"单 Agent + 多 skill 的工具调用"，与 `agent` 型一致
- `team` 型需要主理人 + SOP 编排，与"用户说一句话、AI 自由挑工具"的架构不匹配，容易互相打架
- 复杂度更低，10 天内更可控

> 若后期演示需要多角色观感，可再评估升级为 `team`。

### 3.2 展示字段规划（plugin.json）

| 字段 | 建议值 |
|---|---|
| `name` / 目录名 | `academic-nav`（kebab-case，创建后不可改） |
| `expertType` | `agent` |
| `categoryId` | `04-DataAI`（数据智能：机器学习、大模型应用） |
| `displayName` | 学术导航 / AcademicNavigator |
| `profession` | 科研学习规划师 |
| `displayDescription` | 中文 40–50 字，突出"从项目反推能力 + 定制科研路线 + 难度匹配前沿推送" |
| `tags` | 固定 3 个：科研路线规划 / 能力画像 / 前沿追踪 |
| `quickPrompts` | 固定 3 个，第一条 = `defaultInitPrompt` |

## 4.5 关键待澄清：静态页面能不能真正对话（**最高优先级**）

### 4.5.1 问题的本质

上一节说"平台已解决部署问题"，需要精确化：

| 平台解决了 | 平台**没有**解决 |
|---|---|
| 发布一个公网可访问的页面 | **页面里的对话能否真正调用模型** |
| 结构化数据在线存储与跨设备同步 | 页面的模型调用通道 |

资料库发布的是**托管好的 HTML**，能展示、能读写数据表，但**本身不带模型能力**。「打开链接 → 输入一句话 → 收到模型回复」这件事**不能想当然，必须验证**。

### 4.5.2 三条路径

| 路径 | 额外成本 | 模型来源 | 判断 |
|---|---|---|---|
| **A · 平台内对话** | 0 天 | 由平台提供 | 最省事，前提是评委能用上专家 |
| **B · 自建对话页** | 约 1 天 | 自己接模型接口 | 最可靠，完全可控 |
| **C · 双交付** | 约 1.5 天 | 专家 + 静态页 | 最稳，但成本翻倍 |

**B 的量级梯度（重要）**：
- **极简 B**：静态页 + 一个 serverless 函数（Cloudflare Workers 一类，免费、无需实名），函数内藏 key 转发给模型。约 100–150 行，半天到一天。
  - 硬要求：**不能是空壳聊天框**，至少要内置一条核心能力路径（如"粘贴项目代码 → 输出带证据的技能点"）
- **完整 B**：完整对话 UI + skill 调度 + 知识库读写 = **回到原全栈方案，4–5 天**。除非确有必要，不要做。

### 4.5.3 一个容易漏掉的坑

**自建后端调模型需要自己的 API 额度。** 赛事发放的 credits 属于 LearnBuddy 平台内，**无法用于自建后端**。国内主流大模型均有免费额度，成本低，但**必须提前申请**——不要拖到最后几天才想起。

### 4.5.4 今天必须澄清的两个问题

**问平台（由 LearnBuddy 自己回答最准）**：

> 用资料库部署到公网的在线页面，页面里的 JS 能不能调用模型？如果不行，平台有没有其他方式让一个公网页面具备 AI 对话能力？

→ 若答案是"能"，则 B 的成本降到接近零，且无需自建后端。

**问赛事方**：

1. 评委如何体验参赛的专家智能体？是安装后在 LearnBuddy 内使用，还是需要另外提供可访问的 URL？
2. 提交专家智能体时，是否还需另附一个公网页面链接作为"可直接访问的在线链接"？
3. 公网页面里的 AI 交互，是否要求评委亲自输入并得到**实时真实**的模型回复？还是静态演示 + 视频演示即可？

→ **第 3 问的答案直接决定要不要做 B。**

### 4.5.5 在此之前的工作原则

**按 C 准备，按 A 推进**：

- 专家智能体是产品主体，无论走哪条路这部分都不会浪费 → 立刻开始做
- B 的极简版作为"保险"，排在 D6 之后；若赛事方明确静态演示可接受，这一天直接省下
- **不要为了保险提前把 B 做完整**

## 5. 立即验证清单（今天做，比写任何代码都重要）

任何一项不成立，方案都要调整：

1. ☐ **跑一次「资料库」能力**，确认「在线页面部署」与「数据表」可用 —— **整个方案的基石**
2. ☐ **建一个最小专家包**（只放一个 `domain-converge` skill），走通 `init → validate → register → 在专家中心对话` 闭环
3. ☐ 用数据表建一张"知识树"表，写入 3 个测试节点，确认能读能写
4. ☐ 生成一个最简可视化 HTML，用资料库发布，**确认真的拿到公网链接**
5. ☐ **向赛事方确认评委的体验路径** —— 专家包如何分发给评委？专家包本身能否作为"可访问的在线链接"？

> **第 5 项必须尽早问清楚。** 赛题同时要求"在线链接"和"源码仓库"，如果专家包不算"在线链接"，就必须补一个公网静态页面作为第二交付物。发一条消息问的成本很低，猜错的成本很高。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 资料库能力不可用或不稳定 | 退回"本地 HTML + localStorage"，同时准备公网静态页作第二交付物 |
| 专家包内 skill 的输出确定性不足 | 每个 SKILL.md 写死输出格式 + `scripts/` 内做结构校验 + 失败重试 |
| 评委体验路径不明确 | **尽早问赛事方**；同时准备静态页面兜底 |
| 预置数据在评委环境不存在 | 首个会话自动检测，为空则引导加载演示种子数据 |
| 过度依赖平台能力导致"工程含量"被质疑 | 把数据模型、校验脚本、页面生成器写成实打实的代码放进 `skills/scripts/` |
