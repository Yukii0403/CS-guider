## 1. 范式的变化

| | 旧设计（页面驱动） | 新设计（对话驱动） |
|---|---|---|
| 入口 | 5 个页面各自发起 | **对话是唯一入口** |
| 交互 | 用户点按钮触发固定流程 | 用户说自然语言，AI 判断该干什么 |
| 调度 | 前端硬编码调哪个 API | **Agent 自主选择 skill** |
| 页面角色 | 入口 + 展示 | **只做展示（视图）** |
| 写入 | 各接口各自写 | **唯一写入点：ChangeSet 确认** |
| 产品定性 | 工具集 | **智能体** |

**为什么值得这么改**：赛题名称就是「学术前沿知识导航智能体」。表格左边那列，评委看到的是"一个前端套了几个表单"；右边那列，评委看到的是"AI 在自主决策"。这是技术创新分（30%）的直接来源。

## 2. 架构总览

```
用户自然语言
   ↓
Agent 判断意图  ← 读三类上下文
   ↓
调用 skill（或不调用，纯对话）
   ↓
产出变更草案 ChangeSet
   ↓
用户在对话里预览、勾选、编辑
   ↓
确认 → 写库 → 所有页面重新读取（自动同步）
```

**三个关键设计**：

1. **只有一个写入点。** Agent 没有"写数据库"这个能力，写库只能由 ChangeSet 被确认后触发。这样"AI 不许直接改知识库"这条红线在架构层面被强制，而不依赖 AI 自觉。
2. **变更永远可见。** 不存在静默修改。用户看不到的修改，就是不存在的修改。
3. **同步是自动的。** 页面和会话的上下文都是**实时从数据库读取**的，所以一旦写库生效，所有页面、所有会话下一次调用都会看到最新状态——**不需要做"推送同步"这件事**。

## 3. Skill 就是 Agent 的工具箱

这是上一轮 skill 化设计最关键的回报：**11 个 skill 天然就是 Agent 的 11 个工具**，不需要为 Agent 重新设计一套。

但要按"是否产生写入"分成两类：

| 类型 | Skill | 行为 |
|---|---|---|
| **生成类**（结果直接展示在对话里） | `domain-converge`、`plan-skeleton`、`expand-stage`、`recommend-papers`、`explain-plan`、`pick-key-files` | 返回内容 → 渲染成消息卡片 |
| **提议类**（产出 ChangeSet，等确认） | `analyze-project`、`parse-learned`、`plan-profile`、`domain-resolve`、`review-domains` | 返回变更项 → 渲染成 ChangeSet 卡片 |

**Agent 的工具列表里没有 `write-database`。** 这是刻意的。

## 4. 三类上下文（你说的"上下文不同但知识库同步"）

| 上下文 | 范围 | 存哪 | 例子 |
|---|---|---|---|
| **会话上下文** | 单个对话 | `ChatSession.messages` | "我前面说过我学过概率论" |
| **任务上下文** | 单次任务 / 当前页面 | 运行时派生 | 用户正在 `/plan` 页 → 优先考虑计划类 skill |
| **知识库上下文** | **全局，跨会话** | 数据库 | 已掌握的知识点、领域树、当前计划 |

**"不同对话上下文不同，但知识库同步"** 的实现方式很简单：会话历史各自独立，但每次调 skill 时**实时从数据库读知识库**（按策略裁剪，见《数据模型与接口契约》读取策略表）。

> 所以不需要做任何同步机制。会话 A 里写进知识库的东西，会话 B 下一步就自动读到了。

**上下文预算**（防止越聊越贵）：每个会话只带**最近 N 轮消息 + 滚动摘要**，早期内容压缩成一段摘要，不全文携带。

## 5. ChangeSet：变更预览与确认

这是整个产品的**信任基础**，也是最值得在演示里展示的一块。

```
ChangeSet {
  id, sessionId, messageId,
  title, summary,              // "将更新知识库 3 项"
  status,                      // pending | applied | rejected | partial
  items: [{
    id,
    op,                        // create | update | delete
    entity,                    // node | domain | plan | planItem | project
    targetId?,
    before?, after,
    reason, confidence,
    checked                    // 用户是否勾选
  }]
}
```

**UI 行为**：
- 每个 item 一行，展示"改什么、改成什么、依据是什么、置信度多少"
- 默认勾选：置信度 ≥ 0.7 的勾上，低的留空让用户自己判断
- 用户可**逐项勾选**、可**直接编辑内容**、可**整体拒绝**
- 三个按钮：`确认同步` / `继续改`（回到对话）/ `全部忽略`

**版本留痕**：`applied` 时给每个 item 记录时间和来源会话，用户可以在历史里回滚。

## 6. 对话 UI 要素清单（直接给 AI coding 用）

| 要素 | 说明 |
|---|---|
| 消息流 | 用户消息右对齐，AI 消息左对齐 |
| **工具调用指示器** | "正在调用 analyze-project" + 完成后折叠成一条细线，可展开看参数与结果 |
| **选项 chips** | 追问时把 2–4 个候选领域渲染成可点按钮，点击即发送 |
| **ChangeSet 卡片** | 变更项列表 + 勾选 + 三个按钮 |
| 流式输出 | 文字逐字出现，工具调用先出现指示器 |
| 输入框 | 支持粘贴大段代码（自动折叠显示） |
| 会话列表 | 左侧或顶部，可新建 / 切换 / 重命名 |
| 同步状态 | 顶部一行"知识库已同步 / 有 3 项待确认" |

## 7. 页面与对话的关系

**页面是视图，不是入口。**

- 对话做成**全局可呼出的侧边面板**，在任何页面都能打开
- 呼出时**带上页面上下文**（"你现在在看计划页，用户说'这个阶段太密了' → 指的是当前计划"）
- 页面上的操作有两种：
  - **精确操作**（勾选、翻页、切换会话、展开阶段）→ 普通 UI 交互，**不调模型**
  - **理解意图**（"太密了""换一个资源"）→ 走对话

> **重要提醒：不要让所有操作都经过 AI 判断。** 否则模型调用次数暴涨、响应变慢、还更容易出错。**AI 负责理解意图，UI 负责精确操作**——这条界线划清楚，体验和成本都会好很多。

### 最终页面清单

| # | 页面 | 承载 |
|---|---|---|
| 1 | 科研路径可视化 | 知识树地图 + 计划时间轴 + 进度 |
| 2 | 每日前沿推送 | 论文卡片流 + 难度匹配 + 推荐理由 |
| 3 | 知识图谱 / 能力画像 | 知识树 + 证据链 + 领域树审阅 |
| 4 | 项目反推 | 粘贴代码 / GitHub 链接 + 反推结果确认 |
| 5 | 计划设计 | 骨架 + 逐阶段展开 + 可视化 |

外加一个**全局对话面板**，不属于任何页面。

## 8. 稳定性策略（演示不翻车）

Agent 架构最大的风险是**不确定性**。四条缓解措施：

1. **显式意图优先。** 用户的话如果能匹配到明确指令（"帮我生成计划""分析这个项目"），**直接路由**到对应 skill，不交给模型判断。
2. **工具描述写到位。** `description` 字段是路由质量的决定因素，必须写清"什么时候该用它、什么时候不该用"。
3. **判断不出来就纯对话。** 不要强行调用工具。宁可回答一句"你是想规划路线，还是想让我分析项目？"。
4. **演示脚本走固定路径。** 关键演示环节用预置输入，且结果已提前验证过（技术红线 4）。

## 9. MVP-0 修订：架构先对，功能后加

**这一版功能可以少，但架构不能错**——你们靠 AI coding，架构错了后面每加一个功能都要返工。

### 9.1 必须进 MVP-0 的架构要素

| 要素 | 为什么现在就要 |
|---|---|
| `ChatSession` + 消息表 | 后面加会话列表不用改表 |
| `ChangeSet` + items 表 | 后面所有写入都走它 |
| Agent 派发循环（意图 → 选 skill → 执行） | 工具从 3 个加到 11 个时不用改代码 |
| ChangeSet 卡片 UI | 最难的 UI，早点做出来 |
| skill 统一契约 `lib/skills/` | 加 skill 就是加文件 |
| 工具调用指示器 | 演示效果的关键 |

### 9.2 功能上仍然只做最小

- 页面：**1 个**（知识树 + 计划混在一起看）
- 工具：**3 个**（`domain-converge`、`analyze-project`、`plan-skeleton`）
- 不做：多会话切换（先单会话）、论文推送、页面拆分

### 9.3 修订后的验收标准

```
对话里输入「我想做多模态」
  → 顶部出现「正在调用 domain-converge」
  → AI 抛出 3 个可选方向（chips）
  → 点击选择
  → 输入「我做过一个 MNIST 分类项目」并粘贴代码
  → 出现「正在调用 analyze-project」
  → 弹出 ChangeSet 卡片：3 个知识点 + 证据 + 置信度，可勾选
  → 确认同步 → 右侧知识树刷新
  → 输入「帮我规划到期末」
  → 生成计划骨架，卡片展示
```

**注意最后一步"右侧知识树刷新"——这就是"知识库同步"最直观的证明，也是最值得录进演示视频的一帧。**

## 10. 风险清单

| 风险 | 表现 | 对策 |
|---|---|---|
| Agent 误判意图 | 该分析项目时去生成计划 | 显式意图优先 + 工具描述到位 + 允许用户手动指定 |
| 上下文膨胀 | 聊久了变慢变贵 | 最近 N 轮 + 滚动摘要 |
| 多会话混乱 | 不知道在哪个会话说过什么 | 会话独立，知识库统一；顶部显示会话名 |
| 变更噪音 | 每次改一点都要点确认 | 同类变更合并成一个 ChangeSet；置信度低的默认不勾 |
| 演示不确定性 | 现场模型判断不同 | 固定演示脚本 + 预置输入 |
