# 开发指南与仓库规范 · v1

> 面向团队成员。回答三个问题：**东西放哪、谁做什么、怎么用 AI 写。**
> 日期：2026-09-17

---

## 一、仓库组织原则

**一个仓库，两条产品线，一个提示词源。**

本作品有两份交付物——LearnBuddy 专家智能体与公网可对话页面——但它们**共享同一套 AI 逻辑**。仓库结构必须让这件事在物理上成立：

```
.
├── README.md            评委第一眼看的东西
├── LICENSE              MIT（方向二必须开源）
├── .gitignore
├── docs/                设计文档（长期有效，不要删）
├── prompts/             ★ 提示词单一事实来源
├── expert/              交付物一：LearnBuddy 专家智能体
├── web-demo/            交付物二：公网可对话页面
└── data/                预置演示数据
```

### 三条硬规矩

1. **提示词只改 `prompts/`**，然后同步到 `expert/` 和 `web-demo/`。任何一方都不许自己另写一份。
2. **`docs/` 里的文档是长期资产**，不要为了"看起来干净"删掉。它们本身就是"开发过程留痕"的证据。
3. **密钥绝不入仓库。** `.env`、`*.key` 都已在 `.gitignore` 里，但**改代码时不要手滑把 key 写死进源文件**。提交前用 `git diff --cached | grep -i key` 自查一次。

## 二、分工：按目录分，不按功能分

**这是新手最重要的一条经验。** 按功能分（"你做前端我做后端"）必然会出现两个人改同一个文件，一冲突就卡住半天。按目录分，冲突几乎不会发生。

| | A · 内容线 | B · 工程线 |
|---|---|---|
| **独占目录** | `prompts/`、`expert/` | `web-demo/`、`data/` |
| **主要工作** | 提示词调优、专家包内容、演示视频与 PPT | 云函数、页面、可视化、部署、仓库整理 |
| **需要写代码吗** | 基本不用（Expert 包是 Markdown） | 用，但模板已经搭好了 |
| **共同负责** | `docs/`、`README.md` | 同左 |

> 谁做哪条线，按你们各自的偏好定。**内容线偏"想清楚"，工程线偏"做出来"**，两条线可以并行，互不阻塞。

## 三、Git 极简工作流

不用学复杂的分支模型。**两个人、十天，下面这套足够了。**

### 第一次

```bash
git clone https://github.com/<你的用户名>/academic-nav.git
cd academic-nav
```

### 每天开始工作前（这一步不能省）

```bash
git pull
```

### 干完一件事就提交

```bash
git add -A
git commit -m "feat: 完成 analyze-project 提示词 v1"
git push
```

### 提交信息怎么写

前缀 + 一句话，够了：

| 前缀 | 什么时候用 |
|---|---|
| `feat:` | 加了新东西 |
| `fix:` | 修了问题 |
| `docs:` | 改了文档 |
| `chore:` | 杂项（整理文件、改配置） |

例：`fix: 修复 analyze 模式温度没生效的问题`

### 遇到冲突怎么办

**不要自己硬解。** 把 `git pull` 的报错原文完整贴给 AI，让它告诉你执行哪几条命令。

### 为什么必须频繁提交

**这不是习惯问题，是得分问题。** 赛制明确禁止"AI 生成完整方案直接提交"，要求保留开发过程留痕。而 `commit` 历史是最硬的证据——它带着时间戳，能证明这个项目是**一天一天长出来的**，不是最后一天生成的。

所以：**每完成一件事就推一次**，不要攒到最后。理想情况下，比赛期间应该有一两百次提交。

## 四、怎么用 AI 写代码

你们全靠 AI Coding，所以"怎么提需求"比"怎么写代码"重要得多。

### 提需求的模板

```
【背景】<一句话说清这个项目在做什么>
【相关文档】<贴上 docs/ 里相关的段落，或 prompts/ 里的提示词>
【要做的事】<一件事，具体到文件>
【产出要求】<只要什么、不要什么、输出格式>
【验收方式】<怎么算做对了>
```

### 五个必须养成的习惯

1. **一次只让它做一件事。** "帮我把整个网站做出来"必然得到一堆不能跑的东西。
2. **让它先给方案，你说"可以"再写代码。** 直接要代码，出错了你连错在哪都看不懂。
3. **改完立刻自己跑一遍。** 不要连改三个地方再测，那样不知道是哪个改坏的。
4. **报错原文贴过去，不要转述。** "它报错了"没有信息量；贴完整堆栈，AI 一眼就能定位。
5. **让它写自检命令。** 比如"给我一条 curl 命令验证这个接口"——比它说"我已经修好了"可靠得多。

### 每次开新对话，先喂这三样

1. 根目录的 `README.md`
2. `docs/数据模型与接口契约_v1.md`
3. 你要改的那个文件本身

否则它会按通用套路给你写，跟你们的架构对不上。

## 五、各阶段产出与完成标志

| 阶段 | A 内容线产出 | B 工程线产出 | 完成标志（两人共同） |
|---|---|---|---|
| D1–D2 | `prompts/` 三段提示词定稿 | 云函数部署成功、页面托管拿到链接 | **链接可访问，且能收到真实模型回复** |
| D3–D5 | 专家包 `plugin.json` + Agent MD + 3 个 SKILL.md | 可视化页面（知识地图 / 计划） | **专家能对话，且能正确读提示词** |
| D6–D8 | 反推效果调优、`data/` 演示种子 | 全链路走查、体验打磨 | **演示脚本跑十遍都不翻车** |
| D9–D10 | 3 分钟视频、PPT | 仓库整理、`README` 完善、提交 | **全部材料就位并自检通过** |

## 六、提交前检查清单

提交当天逐条打勾，**每一条都要亲自点一遍**：

- [ ] 公网链接在**手机流量**下能打开（不要只在校园网测）
- [ ] 页面输入一句话，能收到**真实的**模型回复（不是预置文案）
- [ ] 源码仓库是**公开**的，`LICENSE` 是 MIT 且已填上姓名
- [ ] `README.md` 里的链接全部点过，没有 `<TODO>` 残留
- [ ] 仓库里**搜不到任何 key**（搜 `sk-`、`api_key`、`Bearer`）
- [ ] 3 分钟视频成片，能完整展示核心功能
- [ ] PPT 完成，含作品简介 / 赛题方向 / AI 能力说明 / 技术方案 / 团队成员
- [ ] **LearnBuddy 对话记录已导出**（见下方待办）
- [ ] `git log` 看得出是一个逐步演进的过程，不是一次性提交

## 七、两件要尽早确认的事

### 1. LearnBuddy 对话记录怎么导出

这是**必交材料**，而且评分里「AI 工具使用」占 25 分。**不要等到 9/26 才想起来。** 这几天就去找出导出/收集方式，确认一下：

- 是导出整个会话，还是可以按条选？
- 有没有长度限制？需不需要自己整理成一份文档？

### 2. 评委怎么体验你们的专家智能体

如果赛事方要求必须有一个"打开就能用的公网链接"，那 `web-demo` 就是主交付物；如果专家智能体被认可，两条线就是并列的。**尽早问清楚**，这决定最后两天的精力分配。

## 八、一条给你们的提醒

十天的项目，**最大的敌人不是技术难，是中途改主意。**

现在方案已经定了：专家智能体 + Web 页面，共享 `prompts/`。**接下来无论遇到什么，都在这个框架里解决，不要再推翻重来。** 每推翻一次，就少掉一天。

如果某个功能做不完——砍掉它，而不是重新设计。**一个做完的 60 分，胜过三个没做完的 90 分。**
