| # | 决策 | 结论 | 理由 |

| 1 | 产品核心 | **用户个性化 + 自由度** | 个性化 = 三个知识入口 + 知识树；自由度 = 计划可随时对话修改 |

| 7 | 计划 | **三级结构 + 落库 + 版本化 + 带顺序** | 不落库就不可复现、不可 diff、不可纠错 |

| 9 | 计划形态 | **按缺口分（不按身份分）**：基础型 / 混合型 / 研究型 | 基础扎实的本科生也该走研究型 |
| 10 | 领域树 | **手工建第一层，其余 AI 增量添加 + 四步查重** | 省手工；靠查重与审阅兜住质量 |
| 11 | 计划生成 | **两段式**：先骨架，再逐阶段展开到天 | 一次生成 56 天会让后半段质量崩 |
| 12 | 科研计划上传 | **初赛不做**（保留为彩蛋候选） | 已确认推迟 |
| 13 | 项目来源 | GitHub 链接 + 手动粘贴（不做 zip） | zip 解析是时间黑洞 |
| 14 | 部署 | 腾讯云 CloudBase 为主，**Vercel/CloudStudio 兜底** | 腾讯云账号尚未注册，需先保底 |

## 1. 领域树 Domain —— 追问收敛的骨架

### 1.1 它解决什么问题

用户在阶段 ① 可能只说得出一句"我想做人工智能"。AI 必须通过追问把方向收敛到具体领域。**追问不能自由发挥**，否则每次路径都不一样，产品质量不可控。领域树就是那条固定下来的收敛路径。

### 1.2 增长机制

| 层级 | 谁建 | 规模 |
|---|---|---|
| 根 + 第一层 | **手工建**（必须做） | 8–12 个节点 |
| 第二层及以下 | **AI 增量添加** | 上限 150 个 |

**第一层的建议节点**（示例，最终由你们定稿）：

计算机视觉、自然语言处理、多模态、生成模型、强化学习与决策、语音与音频、图与推荐、机器学习理论、智能体、AI4Science

第一层必须手工，因为**追问的第一跳就是这一层**——"你更偏视觉、语言、还是多模态？"这句话的选项就来自它。

### 1.3 追问策略：选项式，不开放式

- AI **先读领域树现有节点**，从中挑 2–4 个作为选项抛给用户
- 只有树里确实没有合适节点时，才走新增流程
- 追问轮数**上限 2–3 轮**，之后必须给一句"我理解你想做的是 X，对吗？"的确认
- 允许用户拒绝收敛 → 生成**探索型计划**（宽而浅）

### 1.4 新增节点前的四步查重（硬约束）

```
① 归一化     小写、去空格与标点
② 别名匹配   同时比对 name 与 aliases[]
③ 包含匹配   上下位包含关系（"多模态" ⊂ "多模态学习"）
④ AI 判定    把候选 top-5 交给模型从中选，不允许它自由造词
```

**四步全部未命中，才提议新建。** 宁可粒度粗一点，也不要产生重复节点。

### 1.5 越界保护

- 节点上限 150，超出时提示人工整理
- 新建节点一律标 `source: ai_added`
- 所有 `ai_added` 节点进入**可审阅列表**（在 `/profile` 页的"领域树"区块），用户可改名、合并、删除
- 合并时要迁移引用（`Node.domainIds`、`Paper.domainIds`）

### 1.6 字段

```
Domain {
  id, name, aliases[], parentId?, level,
  arxivCategories[],   // 用于论文抓取
  keywords[],          // 用于论文与知识点匹配
  source: seed | ai_added,
  createdAt
}
```

## 2. 知识树 Node

### 2.1 结构与状态

- 五级：`category`(L1) → `subfield`(L2) → `course`(L3) → `unit`(L4) → `topic`(L5)
- **`status` 与 `confidence` 只存 L5（知识点）**
- L1–L4 的状态**由子节点聚合计算**，不落库：
  - 子节点 mastered 占比 ≥ 0.8 → mastered
  - ≥ 0.2 → learning
  - 否则 locked
- 保留 `manualOverride`，允许人工或 AI 覆盖聚合结果

### 2.2 描述成本红线

| 层级 | 是否写 1–2 句 summary |
|---|---|
| L1–L3 | ✅ 必须（约 240 节点 × 50 字 ≈ 1.2 万字，可接受） |
| L4–L5 | ❌ 只写短标签，**按需懒生成** |

若把整棵树展开到 L5，约 1.4 万节点，即使每级 30 字也约 40 万字，**任何模型都读不下**。

### 2.3 字段

```
Node {
  id, parentId?, level(1-5), name, summary?,
  category,           // L1 分类枚举
  domainIds[],        // 关联领域，用于论文匹配
  status,             // locked | learning | mastered（仅 L5 有值）
  confidence,
  manualOverride,
  source,             // seed | ai_inferred | user_confirmed
  updatedAt
}
```

## 3. Project 与 Evidence

### 3.1 存储形态：仓库式记录

```
Project {
  id, name,
  source,             // github | manual（初赛不做 zip）
  sourceUrl, description, readme,
  languages[],        // [{ lang, ratio }]
  fileTree[],         // 只存路径列表，不存内容
  keyFiles[],         // [{ path, reason, content }] — AI 挑出的 5–10 个
  domainTags[],
  analyzedAt, createdAt
}

Evidence {
  id, projectId?, nodeId,
  type,               // code | course | self_report | conversation
  ref, detail, createdAt
}
```

**绝不存整个仓库的代码**，只存被 AI 挑中的关键文件内容。

### 3.2 关键机制：先选文件，再读内容

```
文件树 + 语言占比 → AI 挑 5–10 个关键文件 → 只读这些文件 + README → 反推能力
```

一个仓库可能几百个文件，全读必然爆上下文。

### 3.3 仓库构成 → 能力分类的映射（实现指南）

| 仓库里能看到的 | 反推出的能力分类 |
|---|---|
| 语言占比 | 编程基础 |
| requirements.txt | 工具基础 |
| 文件命名（resnet.py） | 理论基础 |
| 训练主脚本（loss / 优化器） | 数学基础 |
| README / 实验记录 | 科研素养 |

> 实际是多对多（`train.py` 同时反映数学基础与工具基础），图上做成一比一只是为了好读。

### 3.4 三个知识入口的防错机制

| 入口 | 输入 | AI 做什么 | 风险 | 防错 |
|---|---|---|---|---|
| 读知识库 | 已有数据 | 直接取状态 | 无 | — |
| **对话录入** | 一句自然语言 | 解析成知识点 + 推定掌握度与置信度 | 自评偏差 | **反问细化** + 确认后写入 |
| 上传项目 | GitHub / 粘贴 | 反推能力 + 证据 | 推理链长、易幻觉 | 只写"证据 + 置信度"，用户确认 |

**反问细化示例**：

> 用户：我学过概率论
> AI：那条件概率和贝叶斯公式算掌握吗？还是只是听过概念？
> → 映射到具体知识点，标上掌握度与置信度，**等确认才写入**

## 4. Paper

```
Paper {
  id, arxivId, title, abstract, url, publishedAt,
  difficulty,         // 1–5
  reason,             // 为什么推给你 ← 必存
  domainIds[],
  matchedNodeIds[],
  cachedAt
}
```

- 数据源：arXiv API（免费、无需 key），按 `Domain.arxivCategories` 拉取
- 推荐依据：用户已掌握的知识点集合 + 计划当前进度
- 初赛**手动触发刷新**，不做真定时任务
- 所有推荐结果**提前缓存**，演示时读库

## 5. Plan / Stage / PlanItem

```
Plan {
  id, title, version, status,        // draft | active | archived
  targetDomainId,
  goal,                              // 一句话目标
  summary,                           // ★ 整体描述与总结（用户明确要的）
  profile,                           // foundation | hybrid | research
  ratio,                             // { knowledge: 80, paper: 20 }
  startDate, endDate,
  dailyMinutes, budgetMinutes,
  constraints[],                     // 如"概率从 4.1 开始"
  excluded[],                        // ★ 明确不做的事
  resources[],                       // 课程简称表 [{ code, name, usage, url }]
  createdAt
}

Stage {
  id, planId, order, title, startDate, endDate,
  description,                       // ★ 阶段级一小段说明
  dailyAllocation[],                 // [{ category, minutes }]
  acceptance                         // ★ 阶段验收标准
}

PlanItem {
  id, stageId, order, date, title,
  resources[],                       // [{ code, chapter, minutes }] 支持多来源
  outcome,                           // ★ 必填：当天完成什么（可验证产出）
  reason?,                           // 可选，AI 觉得必要时才填
  durationMin,
  status,                            // todo | doing | done | skipped
  nodeIds[]
}
```

### 5.1 三种计划形态（按缺口分，不按身份分）

| 形态 | 适用 | 知识线 : 论文线 |
|---|---|---|
| 基础型 | 缺口大 · 想系统补 | 80 : 20 |
| 混合型 | 有基础 · 想尽快上手 | 50 : 50 |
| 研究型 | 前置扎实 · 目标做研究 | 25 : 75 |

配比是 AI 建议的起点，**用户可以手动改**。

### 5.2 生成规则（AI 必须遵守）

1. **两段式**：先出骨架（goal + summary + 阶段划分 + 每阶段说明），用户确认后再逐阶段展开到天
2. **每 1–2 周必须留一个缓冲日**，不允许排满
3. 每个 `PlanItem` 必须有可验证的 `outcome`
4. 时间分配总和不得超过 `budgetMinutes`，超出时提示需要裁剪
5. 整个阶段可单独重新生成，不影响其他阶段

### 5.3 自由度的实现方式

计划是**可编辑的结构化对象**（不是 Markdown），用户可：

- 跳过某阶段 → AI 重新计算后续
- 换资源 → AI 换等价资源
- 改节奏（"每周只能 5 小时"）→ AI 重排到天
- 手动加 / 删条目
- 追问"为什么排成这样" → AI 解释

> **注意：自由度 ≠ AI 输出随机。** 自由度是"用户随时可改，改了 AI 跟着重排"。

## 6. 接口契约

统一返回格式（所有接口一致）：

```
{ "ok": true, "data": {...} }
{ "ok": false, "error": "可读的错误信息" }
```

所有 LLM 调用走 `lib/llm.ts`，内部用 Zod 校验输出结构，失败自动重试 ≤2 次，仍失败返回 `ok:false` 由前端展示兜底文案。

### 阶段 ① 定位目标领域

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/domains` | 领域树（供选项式追问） |
| POST | `/api/domains/converge` | 一轮追问：输入用户回答，返回下一轮选项或确认结论 |
| POST | `/api/domains/resolve` | 四步查重：返回 `{ matched }` 或 `{ proposal }` |
| POST | `/api/domains/confirm` | 确认新建领域节点 |
| PATCH | `/api/domains/:id` | 改名 / 合并 / 删除（审阅入口） |

### 阶段 ② 诊断知识现状

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/knowledge/tree` | 知识树，支持 `?maxLevel=` 裁剪（按场景下探） |
| GET | `/api/knowledge/nodes/:id` | 节点详情 + 证据链 |
| PATCH | `/api/knowledge/nodes/:id` | 修改状态 |
| POST | `/api/profile/parse-text` | 对话录入：自然语言 → 候选知识点（反问细化，不落库） |
| POST | `/api/profile/confirm` | 确认后写入知识库 |
| POST | `/api/projects/analyze` | 项目导入 → 候选技能点 + 证据 + 置信度（不落库） |
| POST | `/api/projects/:id/confirm` | 确认后写入知识库 |

### 阶段 ③ 确定计划形态

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/plan/profile` | 依据缺口与意图判定形态与配比，返回可调整的建议 |

### 阶段 ④ 生成计划

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/plan/skeleton` | 生成计划骨架（goal + summary + 阶段划分） |
| POST | `/api/plan/:id/stage/:sid/expand` | 展开单个阶段到天 |
| POST | `/api/plan/:id/commit` | 确认落库（生成新版本） |
| GET | `/api/plan/:id` | 计划详情（含 stages 与 items） |
| PATCH | `/api/plan/items/:id` | 修改任务状态 → **回写知识树节点状态** |

### 阶段 ⑤ 持续演进

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/papers/recommend` | 按 `planId` 或 `nodeIds` 推荐论文 |
| GET | `/api/papers` | 已缓存论文列表 |
