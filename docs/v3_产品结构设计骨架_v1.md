## 一、一句话结论

**这不是"三个功能"，而是「一个知识库 + 三个视图」。**

知识库是唯一的事实来源。对话页是它的输入口，路径页和推送页是它的两种输出。
把这个关系摆正，剩下所有设计问题都变成"这个动作该不该写库、写哪张表"。

---

## 二、形态选型（先定这个，后面才不会打架）

| 组件 | 形态 | 为什么 |
|---|---|---|
| AI 对话页 | **宿主**，不是 skill | 所有 skill 都跑在这里。它自己不需要能力 |
| 科研路径可视化页 | **视图**，不是 skill | 它是知识库的只读投影，没有独立能力可言 |
| 每日前沿推送页 | **视图 + 一个 skill**（`paper-radar`） | 拉取和筛选是能力，展示是视图 |
| 知识库写入 | **一个 skill**（`library-update`） | 写入必须统一契约，**不允许每个 skill 自己写库** |

**结论：不做专家团（team）。** 你们的范式是"单 Agent + 多 skill 工具调用"，
而 team 型的本质是多角色按固定 SOP 协作，它会和"用户说一句话、AI 自己判断调哪个能力"直接冲突。

## 三、信息架构：一个库，三视图

```
              ┌─────────────── 知识库（唯一事实来源）───────────────┐
              │  domains · nodes · projects · evidence · plans     │
              │  plan_stages · plan_items                          │
              └───────────────────────┬───────────────────────────┘
                     ▲ 写入（草案→确认）        │ 读取（摘要注入）
                     │                          ▼
    ┌────────────────┴───────────────────────────────────────────┐
    │  AI 对话页（宿主）                                          │
    │  自然语言 → AI 判断 → 调 skill 或纯对话                      │
    └────────────────┬───────────────────────────────────────────┘
                     │ 两种只读投影
        ┌────────────┴────────────┐
        ▼                         ▼
   科研路径可视化页            每日前沿推送页
   （plans 的投影）          （nodes + 领域偏好的投影）
```

**关键推论**：三个页面之间**不直接通信**。所有数据流动都必须经过知识库。
否则会出现"路径页改了计划，推送页还在用旧数据"这种经典的一致性问题。

## 四、知识库（必须，且是整个产品的核心）

沿用已定稿的 7 张表，**一张不加、一张不减**（结构归开发者）：

| 表 | 存什么 | 关键字段 |
|---|---|---|
| `domains` | 领域树（追问收敛的骨架） | id, name, aliases, parent_id, level, arxiv_categories, source |
| `nodes` | 知识树，五级：分类→子学科→课程→单元→知识点 | id, parent_id, level, name, category, summary, status, confidence, domain_ids |
| `projects` | 项目（证据来源） | id, name, source, source_url, readme, languages, file_tree, key_files, domain_tags |
| `evidence` | 证据，把项目挂到知识点上 | id, project_id, node_id, type, ref, detail |
| `plans` | 计划 | id, title, version, target_domain, goal, summary, profile, ratio, daily_minutes, constraints, excluded |
| `plan_stages` | 阶段 | id, plan_id, order, title, start_date, end_date, description, acceptance |
| `plan_items` | 日任务 | id, stage_id, order, date, title, resources, outcome, reason, duration_min, status |

**会话（conversations / messages）不算知识库。** 它属于对话页，独立命名空间。
这个边界必须守住：**对话可以丢，知识库不能丢。**

### status 只挂在最细的知识点层

```
未接触 / 学习中 / 已掌握 / 需复习
```

上层（课程、子学科、分类）的状态**由下层聚合算出**，不手工维护。
这是整个知识库最容易被写坏的一处：一旦允许上层直接改状态，下层和上层就会互相矛盾。

### 存哪（★ 必须你先定）

| 方案 | 能做到什么 | 代价 |
|---|---|---|
| A. 浏览器 localStorage | 今天就能跑通全流程 | 换设备/清缓存就没了。**演示时如果换浏览器，知识库是空的**——这是有风险的 |
| B. Cloudflare D1 | 真持久化，换设备可见，可加多用户 | 要建库 + 绑定 + 写接口，约半天 |
| C. LearnBuddy 资料库 | 专家版天然用它，生态内一致 | Web 版用不上 |

**建议 B**：知识库一旦是核心，"刷新就没了"会直接毁掉演示的可信度。
但 A 可以作为 B 的降级路径（D1 不可用时退回本地，界面上明说）。

## 五、Skill 清单与路由（5 个）

| skill | 用户会说的话 | 写库？ | 确认粒度 |
|---|---|---|---|
| `domain-converge` | "我想做 AI，但不知道具体方向" | 写 `domains` | 新增节点时逐条确认 |
| `analyze-project` | 粘贴代码 / "我做过 X 项目" | 写 `nodes` + `evidence` + `projects` | **逐条勾选**（置信度 ≥0.7 默认勾） |
| `plan-skeleton` | "帮我排个到 12 月的计划" | 写 `plans` + `plan_stages` + `plan_items` | 骨架一次、每个阶段展开一次 |
| `library-update` ★新增 | "我学过数据结构" / "把我知识库里 X 标成已掌握" | 写 `nodes` | **逐条勾选** |
| `paper-radar` ★新增 | "今天有什么可读的论文" | 只读（收藏另算） | 无写入，纯查询 |

**路由由模型自己判断，界面上永远没有模式按钮。** 判断不出来就正常对话，不套用任何 skill。
一次回答可以同时用多个 skill（先反推能力，再据此排路线）。

### 两个新 skill 的触发描述成稿

写进 SKILL.md 的 frontmatter，是**英文**（与现有三个保持一致）：

**`library-update`**
```yaml
description: "Use when the user states what they have studied, asks to update their knowledge profile, or wants a knowledge point marked as mastered / in-progress / needs-review ('I took a data structures course', 'mark linear algebra as mastered'). Resolves the stated course or topic to concrete knowledge points in the five-level tree, asks one clarifying question when the statement is too coarse to verify, then proposes a draft diff for the user to confirm. Do NOT use when the user is only asking a conceptual question, and never write to the knowledge base without explicit confirmation."
```

**`paper-radar`**
```yaml
description: "Use when the user asks what to read next, what is new in their field, or for a daily digest of recent papers ('what's new in multimodal retrieval', 'find me something to read today'). Selects papers whose difficulty matches the user's current knowledge points, explains why each one is recommended to this user, and never invents titles, authors, venues or links — if no real source is available, say so explicitly. Do NOT use for summarising a paper the user pasted (that is plain conversation)."
```

## 六、写入确认流程（★ 你提的"预览后决定保存还是继续改"）

**每次写库都走同一套 UI：消息里内嵌一张「变更卡片」。**

```
┌─ 建议更新知识库 ─────────────────────────┐
│ ☑ 新增  数据结构 › 树 › 二叉树          │
│         依据：你说"学过数据结构"          │
│         置信度 0.7                       │
│ ☐ 修改  算法基础 › 排序 → 已掌握         │
│         依据：你提到能手写快排            │
│         置信度 0.6（建议你确认）          │
│ ☑ 新增  项目：MNIST 图像分类             │
│         依据：上传的 train.py            │
├──────────────────────────────────────────┤
│  [保存同步]   [继续改]   [全部忽略]       │
└──────────────────────────────────────────┘
```

四条硬规则：

1. **默认勾选按置信度**：≥0.7 建议勾选，<0.6 留空并提示"建议你确认"。
2. **AI 永远不静默写库**。禁止"我已经帮你记下了"这种事后再报。
3. **「继续改」不是取消**，是让 AI 重新生成一版草案 —— 用户不该被迫在"接受"和"从头再来"之间二选一。
4. **保存同步必须可撤销。** 保留最近 N 次变更的快照，界面上给一个"撤销上次同步"。

第 4 条是我要额外强调的：**知识库一旦成为核心，一次误点就会把错误固化下去，而且用户不容易发现。**
可撤销不是锦上添花，是这个设计的必要组成部分。

## 七、自由度：用户能改什么、不能改什么

你强调"个性化 + 自由度"，那就要把自由度的边界写清楚，否则会变成"什么都能改"导致结构失控。

| 层面 | 用户能改 | 说明 |
|---|---|---|
| 领域方向 | ✅ 随时改、可拒绝收敛、可手动加领域 | 探索型路线是合法需求 |
| 知识状态 | ✅ 手动改任意知识点的 status | 自评也是证据，只是置信度低 |
| 计划 | ✅ 改期限、改配比、改每日投入、跳过某阶段、手动加条目 | 计划是建议，不是判决 |
| 知识树结构 | ⚠️ 可以加节点，但**要走查重** | 结构归开发者，加节点要提草案 |
| 五级分层的层数 | ❌ 不能改 | 改了整套聚合逻辑就废了 |
| 一级分类（五类） | ❌ 不能改 | 同上 |

一句话原则：**内容随便改，结构改了要问。**

## 八、UI：Codex 风格怎么落地

你要的是那种"像文档、不像聊天"的界面。可复刻的四个要点：

| 要复刻 | 具体做法 |
|---|---|
| **左侧固定侧栏** | 约 220px：顶部「新对话」；中部项目区；下部按时间分组的对话列表；底部账号与设置。用一条 0.5px 分隔线，不要卡片阴影 |
| **消息不用气泡** | 内容左对齐、通栏、约 720px 宽。用户消息也不用气泡，用浅灰块区分。**这是"像文档"观感的主要来源** |
| **底部 composer 两行** | 第一行输入区，第二行工具栏：左侧 `+`（附件/粘贴代码）+「请求批准」；右侧模型名 + 发送圆钮。圆角约 16px，整体微微上浮 |
| **「请求批准」** | 正好对应我们的「保存同步」——**这个按钮名比"确认"更准确**，直接借用 |

**不要复刻的**：模型选择器（我们只有一路模型，显示成只读文字即可）、语音按钮、PR/定时任务/插件入口（Codex 特有）。

配色**不要跟着换成深色**：现有浅色（`#F7F7F5` 底 + `#185FA5` 强调）与 Codex 的中性浅色本来就接近，改色是纯风险。

## 九、能力边界（✅ 能做 / ❌ 不做 / ⚠️ 必须转介）

| ✅ 能做 | ❌ 不做 | ⚠️ 必须转介 |
|---|---|---|
| 选项式追问，把模糊兴趣收敛到具体子方向 | 代写论文、实验报告、作业；改写他人成果冒充原创 | 培养方案、学分、毕业要求 → 导师 / 院系教务 |
| 从代码与项目里抽证据，输出带置信度的知识点；无证据时明说"未发现证据" | 伪造、美化、选择性丢弃实验数据 | 科研压力、焦虑、失眠 → 学校心理咨询中心 |
| 维护知识库画像，按五个一级分类归位 | 编造论文标题、作者、会议、DOI、链接 | 署名顺序、数据归属、疑似剽窃 → 导师 / 学术委员会 |
| 生成分阶段路线（先骨架后展开），每天带可验证 `outcome` | 代替导师或评审下判断（"能不能投""能不能毕业"） | 投稿选刊与录用概率 → 说明需导师与同行判断，不给结论 |
| 按掌握度推送难度匹配的论文，并说明"为什么推给你" | 承诺结果（"学完就能发论文""保过"） | 个人身份敏感信息 → 不索取、不留存 |
| 全程可预览、可撤销，用户始终能改 | 静默写库；用户说"不用了"还反复劝 | — |

## 十、三个必须提前知道的风险

**1. 推送页在没有真实数据源之前，不许编论文。**
`paper-radar` 要么接 arXiv / OpenAlex 这类真实接口，要么在页面上**明确标注"示例数据"**。
编一条看起来很像真的论文标题，是这个产品最容易翻车的地方，也是评审最不能容忍的一类问题。

**2. 上下文隔离 + 知识库共享，意味着注入的是"摘要"不是全量。**
每个对话上下文独立，但都要能读到知识库。**不要把整库塞进 system prompt**——
知识点上百条之后会直接把上下文撑爆。做法是每次按当前对话主题做一次检索，只注入命中的那几十条。

**3. 三个页面共用一份数据，就会出现"改完没生效"的困惑。**
路径页改了期限，推送页的难度匹配也要跟着变。所以写入必须走同一条确认链路，
并且界面要有明确的"最后同步时间"。

## 十一、上线自检清单

**格式**
- [ ] 每个 skill 的 SKILL.md frontmatter 有 `description`，且写明了"什么时候**不**用它"
- [ ] 提示词正文里没有反引号、没有 `${`（会截断 worker.js 的模板字符串）
- [ ] `node web-demo/scripts/check-prompts.mjs` 通过

**数据**
- [ ] 知识库状态只写最细的知识点层，上层靠聚合
- [ ] 任何写库都有确认卡片，没有静默写入的路径
- [ ] 撤销可用（至少能回退上一次同步）
- [ ] 换设备能看到自己的知识库（取决于你选 A 还是 B）

**体验**
- [ ] 首页没有任何预置输入，也没有模式按钮
- [ ] 追问最多 2–3 轮后一定落地成一个判断
- [ ] 计划页能勾选、能复制、能清空，空状态有引导
- [ ] 推送页的论文都点得开（或明确标了示例）

**合规**
- [ ] 不编造文献；不确定就说不确定
- [ ] 不承诺结果，不做无资质的专业结论
- [ ] 密钥不下发前端；`.env` 不在版本控制里

## 十三、上线后该看什么信号

| 看到的现象 | 说明哪里有问题 | 怎么改 |
|---|---|---|
| 用户反复说"还有别的吗" | 领域树第一层覆盖不够 | 补节点，但不超过 12 个 |
| 用户跳过确认卡片直接聊下一句 | 卡片太啰嗦或出现太频繁 | 合并同一次回答里的多个变更 |
| 知识库里同一门课出现两次 | 查重没生效 | 收紧别名匹配，`dedupe.py` 加同义词表 |
| 用户从不打开路径页 | 它没成为对话的自然出口 | 生成计划后自动打开，并给一个固定入口 |
| 用户抱怨推送的不想看 | 难度匹配只看了领域，没看掌握度 | 把 `nodes.status` 真正接进筛选 |
| 用户把知识库全清空重来 | 收敛过程太烦，或写错了没法改 | 先修撤销，再加"跳过"选项 |
