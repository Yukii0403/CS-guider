## 2. 定位与人设

### 2.1 现有定位（`docs/需求概要…§1`）
> 从你已有的项目和代码里反推真实能力水平，据此生成可执行的学习路线，并按你的学习进度持续推送难度匹配的论文。

这句是**产品定位**，写得很好：有输入（项目代码）、有动作（反推）、有产出（路线 + 论文）、有差异化（不看自评看证据）。**保留，不要动。**

### 2.2 但缺"人设"——用户看见的是谁？

`prompts/chat.md` 只写了「服务对象」与「职责」，没有姓名、身份、语气基调。用户第一次打开专家的体验是这样的：

> 现有：一个没有名字的功能描述。
> 应该有：一个说得出自己是谁、会怎么跟你对话的角色。

**建议基调：干脆型 + 严谨型**，不要温暖型。理由：产品输出的每一条结论都挂着置信度和证据，人设如果偏"哄人"，会和"我会明说我看不出来"的能力自相矛盾——这就是典型的人设与能力割裂。

### 2.3 成稿：首次问候语（`defaultInitPrompt`，可直接粘贴）

```
你好，我是科研学习规划师。先告诉我你想切入哪个方向——说不清也没关系，
我会给你几个选项帮你收敛。你也可以直接粘一段写过的项目代码，我从里面
反推你实际掌握了哪些知识点，比自评问卷准。
```

### 2.4 成稿：给 Agent MD「角色定义」章节的一句人设

```
你是「学术前沿知识导航」，身份是科研学习规划师，服务刚开始接触科研的
本科生与研究生。说话干脆、给结论、给理由，不寒暄、不鼓励式空话。你的
每一条能力判断都必须能追溯到证据；没有证据时说「未发现证据」，而不是
给一个听起来合理的猜测。
```

## 3. 形态选型

| 选项 | 是否选 | 理由 |
|---|---|---|
| **专家（agent 型）** | ✅ **选** | 产品范式是"单 Agent + 多能力单元调用"，与 agent 型一致；对话/调度/会话管理由平台提供 |
| 专家（team 型） | ❌ | team 型靠主理人 + SOP 编排，与"用户说一句话、AI 自由挑能力"直接打架 |
| 技能（独立 Skill） | ❌ | 技能是**被自动调用**的能力单元，没有独立人设与对话界面，撑不起"路线规划"这种多轮收敛的交互 |
| 自建 Web 应用 | ⚠️ 降级为第二交付物 | 已由 `web-demo/` 承担，用于满足"公网可访问链接"这条硬要求 |

**文档里的选型理由成立，不用改。** 补一句可以直接写进 PPT 的话：

> 我们选专家而不是自建全栈，不是因为它更省事，而是因为**对话、调度、上下文管理这三件事平台做得比我们好**——把时间花在只有我们能做的部分：知识分层与证据化能力推断。

## 4. 提示词结构评估（本轮最实质的缺口）

### 4.1 一个能力单元应有的两层结构

```
第 1 层 · 触发描述   → 系统/模型据此判断「什么时候该启动我」
第 2 层 · 正文       → 启动了之后「具体怎么做」（角色、流程、输出格式、约束）
```

`prompts/*.md` 目前**只有第 2 层**。在自建 Web 里这不是问题——因为 `worker.js` 用 `mode: 'chat' | 'analyze'` 显式指定了用哪段提示词，路由由代码做完了。**但在专家包里，路由是模型自己做的**：模型只能读到 SKILL.md 的 `description`，读不到正文。**没有触发描述 = 这个技能要么永远不被调用，要么到处被误调用。**

### 4.2 逐段诊断

| 提示词 | 第 2 层（正文） | 第 1 层（触发描述） | 「什么时候不该用」 | 后果 |
|---|---|---|---|---|
| `chat.md` | ✅ 有职责 + 5 条原则 | ❌ 无 | ✅ 有（末段"防套用"） | 防套用做得对，但模型不知道**何时该主动走**领域收敛路径 |
| `analyze-project.md` | ✅ 输出格式 + 5 条规则 | ❌ 无 | ❌ 无 | 用户贴一段报错日志、一段 YAML 配置，也会被当成"项目代码"反推 |
| `plan-skeleton.md` | ✅ 输出格式 + 6 条规则 + 两段式 | ❌ 无 | ❌ 无 | 用户说"帮我排个复习计划"，会强行套进科研计划模板 |

`chat.md` 末段那句"如果用户的输入与…无关，就当作普通对话正常回答，不要强行往这三个方向拽"是**全文最有价值的一句**——它就是「什么时候不该用」。**`analyze-project.md` 和 `plan-skeleton.md` 必须各补一句。**

### 4.3 成稿：三段触发描述（可直接粘贴到 SKILL.md frontmatter 的 description）

**`domain-converge`**
```
当用户表达想学/想做某个方向但表述模糊（如"我想做人工智能""帮我找个科研方向"），
需要先把方向收敛到具体子方向时使用。每次给出 2–4 个候选项让用户挑，最多追问
2–3 轮后必须给出确认句。若用户已经说清了具体方向，跳过本技能直接进入能力诊断。
```

**`analyze-project`**
```
当用户粘贴代码、项目文件结构、requirements.txt、README，或说"这是我做过的项目"
"帮我看看我会什么""分析一下我的代码"时使用。仅在输入包含可读的代码或工程结构时
使用；若用户只是问某个知识点的定义、或在讨论学习安排，不要调用本技能。
```

**`plan-skeleton`**
```
当用户已确定目标方向、且已掌握情况可知（已诊断过或用户明确说不用再测），需要一份
分阶段学习路线时使用。第一次只输出骨架（目标/缺口/阶段/时间预算/明确不做），
用户确认后才逐阶段展开到天。若用户只是问某个知识点怎么学、在闲聊或抱怨进度，
不要调用本技能。
```

### 4.4 一条要修的仓库规矩

`prompts/README.md` 写的是「两个地方必须保持同一份文本」。精确化后应该是：

- **正文**（第 2 层）→ 必须同一份，`prompts/*.md` 是唯一来源
- **触发描述**（第 1 层）→ 只存在于 `expert/` 的 SKILL.md frontmatter 与 `web-demo/worker.js` 的路由逻辑里，**不来自 `prompts/`**

否则两周后你会发现"同一份文本"这句话解释不了为什么 SKILL.md 多出一段。建议在 `prompts/README.md` 补一张三行映射表：`prompts 文件 → SKILL.md frontmatter description → worker.js 的 mode`。

## 5. 能力边界与红线（第二处实质缺口）

### 5.1 现状
提示词里只有一条红线：**严禁编造论文标题、作者、会议名和链接**（`chat.md` 第 4 条 + `analyze-project.md` 规则 1）。这条写得非常好，是学术场景的底线。

但它**只覆盖了"事实性编造"，没有覆盖"学术诚信"与"专业边界"**。一个面向本科/研究生的科研助手，最容易被投诉、也最容易出事的恰恰是后者。

### 5.2 能力边界表（成稿，可直接写进 Agent MD 的「能力边界」章节）

| ✅ 能做 | ❌ 不做（明确拒绝并说明原因） | ⚠️ 必须转介 |
|---|---|---|
| 选项式追问，把模糊兴趣收敛到具体子方向 | 代写论文、实验报告、作业，或改写他人成果冒充原创 | 培养方案、学分、毕业要求等正式学业决策 → 导师 / 院系教务 |
| 从代码/项目结构抽取证据，输出带置信度的知识点；无证据时明说"未发现证据" | 伪造、美化、选择性丢弃实验数据；建议"先把图做出来再补实验" | 科研压力、焦虑、失眠等身心困扰 → 学校心理咨询中心 |
| 对照目标方向列缺口，按五个一级分类归位 | 编造论文标题、作者、会议名、DOI、链接——不确定就说不确定 | 署名顺序、数据归属、疑似剽窃等争议 → 导师 / 学院学术委员会 |
| 生成分阶段路线（先骨架后展开），每个条目必带可验证 `outcome` | 代替导师或评审下判断（"这篇能不能投""这个方向能不能毕业"） | 投稿选刊与录用概率 → 说明这需要导师与同行判断，可提供公开信息梳理但不给结论 |
| 解释计划的排布理由（为什么这个阶段在前） | 承诺结果（"学完就能发论文""保过""包拿 offer"） | 涉及个人身份的敏感信息 → 不索取、不留存 |
| 按难度匹配推荐前沿论文，说明"为什么推给你" | 直接写库——**架构上就不给这个能力**（无 `write-database` 工具） | — |

### 5.3 为什么"必须转介"这三项不用长文，一句话就够

护栏的价值在于**能被真正触发**。用户说"我最近做实验一直失败，很焦虑"时，模型需要一条明确指令，而不是一段"仅供参考"的空话。上面每一条都写成了"触发条件 → 转到哪里"，这就是可执行的话术护栏。

### 5.4 建议补进 `prompts/chat.md` 的两条原则（可直接粘贴）

```
6. 你不代写论文、实验报告与作业，也不帮助伪造或美化实验数据。用户提出这类
   请求时，说明原因并改为提供方法层面的帮助（如"怎么设计对照实验"）。
7. 涉及培养方案、投稿录用、学术争议这类需要导师或院系判断的问题，说明这超出
   你的范围，并指出应该找谁，而不是给出一个看起来专业的结论。
```

## 7. 技能封装设计

### 7.1 专家和技能，调用方式根本不是一回事

| | 专家（Expert） | 技能（Skill） |
|---|---|---|
| 谁选择它 | **用户主动选中/呼出** | **模型自己判断是否加载** |
| 用户看得见吗 | 看得见——他知道"我在用学术导航" | 看不见——他只看到结果 |
| 靠什么被选中 | 名称、职业、能力介绍、推荐提示词 | **只有 `description` 一句话** |
| 有没有人设 | 有，人设是它的核心 | 没有，它是纯能力 |
| 边界写在哪 | Agent MD 的能力边界章节 | description 里"什么时候不要用" |

**一句话记住**：专家是"你点开的门"，技能是"门后面 AI 自己决定要不要拿出来的工具"。所以技能描述写不好 = 这个技能等于不存在。

### 7.2 一个必须提醒的坑：不要把 11 个 skill 直接搬进专家包

`docs/AI_Skill设计与最小版本_v1.md` 里的 11 个 skill，原本是**自建应用里按文件拆分的 TS 模块**——路由由代码做，模块之间边界清楚。

搬进专家包后，路由变成**模型在 11 个 description 之间做选择**。这会带来两个问题：

1. **描述互相抢**：`domain-converge` 与 `domain-resolve`，`plan-skeleton` 与 `expand-stage`，从 description 层面很难写出一刀切的边界，模型会随机挑
2. **上下文成本**：11 份 SKILL.md 的说明常驻，挤占本就有限的上下文

**建议：初赛只落 3 个 SKILL.md**（与 `prompts/` 的三个文件一一对应），其余 8 个**降级为 Agent MD「工作流程」章节里的 SOP 步骤**——也就是"第 3 步，查重后再提议新建节点"这样的文字，而不是独立的技能文件。这与 D2 排期（3 个 skill）也一致。

> 判断标准很简单：**需要独立触发条件、且输出格式与主流程明显不同的，才拆成技能。** 只是主流程里的一步，就写在 SOP 里。

```

├── .codebuddy-plugin/plugin.json     展示字段（第 6 节成稿）
├── agents/academic-nav.md            人设 + 五阶段 SOP + 能力边界表 + 输出规范
├── avatars/expert.png
└── skills/
    ├── domain-converge/
    │   ├── SKILL.md                  frontmatter(description=触发描述) + 正文(取自 prompts/chat.md)
    │   └── references/
    │       └── domain-tree.md        ★ 领域树第一层 8–12 节点清单（见 7.4）
    ├── analyze-project/SKILL.md      触发描述 + 正文(取自 prompts/analyze-project.md)

```

**注意**：Agent MD 的 frontmatter **不要声明 `tools` 字段**。

### 7.4 领域树第一层：整个设计里风险最高的一处未落地项

`docs/需求概要` 与 `docs/数据模型与接口契约` 都确立了「**追问用选项式，不用开放式**」，而选项**来自领域树第一层 8–12 个节点**。目前 `data/README.md` 标注「待建」。

如果专家包上线时这个清单还不存在，会发生什么：

```
用户：我想做人工智能
AI（无节点清单）：你具体想学人工智能的哪个方向呢？   ← 退化成开放式提问
```

而产品的记忆点恰恰是「一次给 2–4 个具体选项让他挑」。**这会直接抹掉体验分里最容易拿的那部分。**

**对策（必须做）**：把第一层节点清单**物理写进专家包**，别依赖 `data/` 目录（评委环境里 `data/` 不会跟着专家包走）。放在 `skills/domain-converge/references/domain-tree.md` 里，SKILL.md 正文加一句"追问候选项只能从本目录 `references/domain-tree.md` 中选取，不得自由造词"。

建议的第一层节点（8–12 个，与 `docs/数据模型与接口契约` 一致）：
`计算机视觉 / 自然语言处理 / 多模态 / 生成模型 / 强化学习 / 语音与音频 / 图与推荐 / 机器学习理论 / 智能体 / AI4Science`

## 8. 上架前自检清单

### 格式类（必须）
- [ ] `name` 为 kebab-case（`academic-nav`），且与目录名一致
- [ ] `agentName` = Agent MD 的文件名
- [ ] `displayDescription` 中文 40–50 字（**本版 48 字 ✅**）
- [ ] `tags` 恰好 3 个
- [ ] `quickPrompts` 恰好 3 个，**第 1 条与 `defaultInitPrompt` 逐字一致**
- [ ] Agent MD frontmatter **不含 `tools` 字段**
- [ ] `avatars/expert.png` 存在，1:1、≥512×512、非透明底
- [ ] `categoryId` 在白名单内（以后台提示为准）

### 合规类（必须）
- [ ] 每个模型名、论文名、链接类表述：无编造，且提示词里有明确禁令
- [ ] 无"保过/包发论文/一定能上"类承诺
- [ ] 能力边界章节含**学术诚信**三条（不代写 / 不伪造数据 / 不代替导师判断）
- [ ] 转介规则成句可触发（不是"仅供参考"）
- [ ] 不收集用户身份与隐私信息
- [ ] 不与平台上已有专家能力重叠（本项目为科研学习规划，重叠风险低）

### 体验类（建议）
- [ ] 首次问候语读起来像一个角色在说话，而不是一段功能说明
- [ ] 用户说不清方向时，第一轮追问**确实给出了 2–4 个具体选项**
- [ ] 低置信度推断**单独列出并主动请求确认**，而不是混进结论
- [ ] 计划类输出里**存在"明确不做"，且每 1–2 周有缓冲日**
- [ ] 所有写入都停在"草案 / 预览"层，用户点确认才落库
- [ ] 空知识库时**主动提示载入演示数据**，并保留"从零开始"的路径

### 本版最可能出问题的三处
1. **领域树清单未内置** → 选项式追问失效（体验分直接受损）
2. **触发描述缺失** → 技能在专家包里不被调用，能力等于不存在
3. **没有学术诚信护栏** → 一旦演示时被问到"能帮我写论文吗"，没有预设答案

## 9. 上线后观察什么、按什么原则改

| 观察信号 | 说明什么 | 怎么改 |
|---|---|---|
| 用户第一轮就说了具体方向 | 领域树第一层粒度合适 | 不动 |
| 用户反复说"还有别的吗" | 第一层覆盖不够 | 补节点，不超过 12 个 |
| 模型答完方向问题就开始长篇输出 | 400 字限制失效 | `chat.md` 的 400 调到 300 |
| 用户贴代码后模型答得像通用点评 | 触发描述或"不能因为…就推断…"被稀释 | 检查 SKILL.md 是否丢规则 |
| 计划被用户大面积手动改 | 缺口判定偏了 | 调 `plan-skeleton` 的缺口分析章节 |
| 用户问"你怎么知道我会这个" | 证据链起了作用，是好信号 | 保留；可把证据展示做得更显眼 |

**改的原则**：一次只改一处，改完立刻用同一条固定输入回测。**不要同时调触发描述和正文**——否则你不知道是哪个改动起了作用。
