# Vibe Coding 工作手册

> 面向本项目的两名成员。回答一个问题：**怎么用 LearnBuddy 把东西真正做出来。**
> 日期：2026-09-17

---

## 一、先想清楚：vibe coding 是什么，不是什么

**是**：你用自然语言描述意图，AI 负责执行，你负责判断和验收。你干的是**产品负责人**的活。

**不是**：把需求丢给 AI，然后等一个成品出来。

### 它能成立的前提

> **你能判断它写对了没有。**

这个前提不靠天赋，靠三件事建立：

| 前提 | 具体做法 |
|---|---|
| **小步** | 一次只做一件事，做完能跑 |
| **可验证** | 每步都有明确的正确标准（跑一次命令、点一下按钮、看一个数字） |
| **可回退** | 每步都提交，坏了能退回去 |

**一旦跳过这三条，vibe coding 就会变成"越写越乱，最后推倒重来"。** 这不是 AI 不行，是流程不成立。

## 二、一次对话的标准循环

```
① 喂上下文 → ② 说清一件事 → ③ 让它先给方案
                                      ↓
⑥ 提交 ← ⑤ 立刻验证 ← ④ 确认后写
```

六个动作，缺一个都会出问题。

### ① 喂上下文

每次开新会话，先粘这三样：

1. 根目录的 `README.md`（这个项目是什么）
2. `docs/数据模型与接口契约_v1.md`（数据结构长什么样）
3. 你这次要改的那个文件本身

**不喂的后果**：它按通用套路给你写，跟你们的架构对不上，你得全部重来。省这一分钟，赔一小时。

### ② 说清一件事

| | |
|---|---|
| ❌ 反例 | 帮我实现知识库功能 |
| ✅ 正例 | 在 `web-demo/worker.js` 里新增一个 mode，叫 `plan`，接收目标领域和已掌握的知识点，返回一份分阶段的计划骨架 |

**判断标准：如果你这句话里出现了"和"、"以及"、"顺便"，就说明你说多了。** 拆成两次。

### ③ 让它先给方案

在需求后面加一句：

> 先告诉我你打算怎么改，我确认之后你再动手。

这一句能省下大量返工。AI 的第一版理解经常和你不一样，**让它先说比让它先写便宜得多**。

### ④ 确认后写

说"可以，开始吧"。

如果它一次动了很多文件，让它逐个说明改了什么、为什么改。

### ⑤ 立刻验证

**这一步绝对不能省。**

| 改了什么 | 怎么验 |
|---|---|
| 能跑的代码 | 真的跑一下（`npm test`、`npm run preview`、打开页面） |
| 文案 / 配置 | 让它把改后的完整内容贴出来给你看 |
| 接口 | 要一条 `curl` 命令，自己敲一遍 |

> **不要相信"我已经修好了"。要一条能证明它修好了的命令。**
> 它说"修复成功"的时候可能是对的，但"可能"在比赛里不够用。

### ⑥ 提交

说一句"提交一下"就行。剩下的（整理改动、写提交信息、推送到 GitHub）由 AI 完成。

**别攒着。** 一次提交对应一件事，历史才读得出来。

## 三、五个把新手拖死的坑

| 坑 | 表现 | 怎么避免 |
|---|---|---|
| **一次要太多** | "帮我把整个系统做出来" | 一句话只做一件事，出现"和"就拆开 |
| **不给上下文** | 它凭空按通用套路写 | 开头三样必喂 |
| **报错只贴一句** | "它报错了" | **贴完整的报错原文**，不要转述、不要截图后打字描述 |
| **改完不验证** | 连改三个地方再测，不知道哪个改坏的 | 改一处，测一处 |
| **攒着不提交** | 最后三天一次性提交几百个文件 | 每天收工说"提交一下" |

## 四、会话怎么管

**一个任务一个会话。** 不要在一个超长会话里从设计聊到部署——上下文会越来越脏，它开始把早期的草稿当成当前的事实。

**长会话里定期让它总结。** 说"把目前已经确定的事总结成一段话"，然后把这段当下一轮的开场。

**发现它开始胡说了，就开新会话。** 三个信号：

- 重复问你刚刚回答过的问题
- 引用已经不存在的文件
- 建议用你们已经废弃的方案（比如又让你去装 Next.js）

**同一个问题连续三轮没解决，就停下来。** 开个新会话，把问题重新描述一遍——通常一次就说对了。不要继续追打。

## 五、这几天具体该说什么

直接复制下面的话去问。

### D1 · 部署云函数

> 我要把 `web-demo/worker.js` 部署到 Cloudflare Workers。我完全没有部署经验，请一步一步带我，每步告诉我点哪里、填什么。请假设我从没注册过 Cloudflare 开始讲。

> 我的函数地址是 `https://xxx.workers.dev`。请告诉我：访问 `/api/health` 正常应该看到什么？如果看到 `"hasKey": false`，我该按什么顺序排查？

### D2 · 专家包骨架

> 请先读 `expert/README.md` 和 `docs/方案转向_专家智能体_v1.md`，然后带我创建 `academic-nav` 专家包。我不会用命令行，请告诉我每一步在 LearnBuddy 里点哪里。

### D2 · 调提示词

> 提示词在 `prompts/analyze-project.md`。下面是我粘贴的代码和它给出的结果——它把"用了 Adam 优化器"推断成"会调参"，置信度给到 0.8，这不对，Adam 是教程里最常见的默认值。请帮我改提示词，让这种情况的置信度降下来，并说明你改了哪一句、为什么。

### 遇到问题时

> 我在做 X，执行了 Y，期望看到 Z，实际看到了下面的报错。请先告诉我可能的原因有哪些，再给出排查顺序，最后才是修复方案。

（注意最后半句：**先诊断，再开药。** 直接让它修，它经常修错地方。）

## 六、五句随时能用的话

| 说这句话 | 作用 |
|---|---|
| 「先别改代码，告诉我你理解的需求是什么」 | 防止理解偏差，最便宜的一次检查 |
| 「你觉得这个方案有什么问题？」 | 让它自我批评，经常真能发现问题 |
| 「给我一条命令验证这个改动」 | 强制它提供验收方式，而不是口头保证 |
| 「只回答，不要改文件」 | 你只是想问个问题时用，避免它顺手乱改 |
| 「刚才那步回退掉」 | 改坏了别硬修，先退回去再说 |

## 七、关于 Credits

初赛每队 2500 credits。**调提示词是最费的一次性投入**，但也是最值的——它是你们产品的核心资产。

几个省着用的原则：

- **别让它反复重写长文档**。先生成骨架，你指出问题，再让它改局部。
- **大文件不要整个贴**。只贴相关段落。
- **调提示词时用短输入**。用一段代表性的代码测，不要每次都贴整个项目。

---

## 八、最后一句

> **你越能说清楚"做完之后我怎么知道它对了"，AI 就写得越准。**

这其实正是你们产品的核心逻辑——`outcome`（当天完成什么）必须是可验证的产出。

**你们在设计产品时想清楚的事，用在自己身上同样成立。**
