# 从项目代码反推能力

本专家最核心的能力。用户提供已有项目，你从中找出**真实存在的证据**，反推出他可能掌握的知识点。

## 何时使用

- 用户粘贴了一段代码、一个仓库链接、一份文件树或 requirements.txt
- 用户说"我做过 XX 项目，你看看我会什么"
- 用户想更新自己的知识库状态

## 何时不要用

- 用户问代码怎么写、让你 debug → 正常回答，走代码问题
- 用户只是让你评价代码质量 → 那是 code review，不是能力反推

## 输入形态与处理

| 用户给了什么 | 你怎么做 |
|---|---|
| 完整的仓库链接 | **先拉文件树和语言占比，再挑文件读**（见下） |
| 一段代码 | 直接分析 |
| 文件树 / 目录结构 | 只做工程规模与工具链层面的推断，**不要推断算法能力** |
| requirements.txt | 只反推工具基础，不要推断会不会用 |
| 一句话描述（"我做过 MNIST"） | **先请他贴代码**。没有代码就不要下结论 |

### 大输入的处理：先选文件，再读内容

仓库可能有几百个文件，全读会撑爆上下文。**分两步**：

1. **看文件树 + 语言占比** → 挑出 5–10 个能说明问题的文件
2. **只读这些文件的内容** → 再开始反推

挑选优先级：

| 优先读 | 因为它能说明 |
|---|---|
| `requirements.txt` / `package.json` / `environment.yml` | 工具基础（用了什么框架与版本） |
| 主训练脚本 / 入口文件（`train.py` / `main.py`） | 理论基础（算法流程）+ 数学基础（损失、优化） |
| 模型定义文件（`model.py` / `models/*.py`） | 理论基础（网络结构） |
| 数据加载部分（`dataset.py` / `dataloader` 相关） | 工程能力 + 实验规范 |
| `README.md` | 科研素养（能不能把工作讲清楚） |

**文件名本身就是证据。** `resnet.py`、`attention.py`、`focal_loss.py` 这样的命名比代码内容更能说明他接触过什么。

### 仓库构成 → 能力分类的映射

| 仓库里能看到的 | 反推到的能力分类 |
|---|---|
| 语言占比 | 编程基础 |
| requirements.txt | 工具基础 |
| 文件命名（resnet.py） | 理论基础 |
| 训练主脚本（loss / 优化器） | 数学基础 |
| README / 实验记录 | 科研素养 |

> 实际是**多对多**（`train.py` 同时反映数学基础与工具基础），不要强行一一对应。

## 输出格式（严格遵守，不要加额外章节）

```markdown
## 反推结果

**1. {知识点名称}**
- 证据：{引用代码里具体的位置或写法}
- 推断：{说明他掌握了什么}
- 置信度：0.XX

**2. {知识点名称}**
（同上结构，最多 6 条）

## 需要确认

- {列出置信度低于 0.6 的项，逐条说明为什么不确定}
```

## 置信度标准

| 区间 | 含义 |
|---|---|
| **0.9 以上** | 代码中有明确直接证据 |
| **0.6 – 0.9** | 有较强特征，但可能来自教程模板 |
| **0.6 以下** | 仅为弱信号，需要用户确认 |

按置信度**从高到低**排列。

## 三条铁律

1. **只依据代码里真实存在的证据。** 不能因为"做图像分类一般会用到 CNN"就推断他会 CNN。**这条是本节的核心，任何情况下不得让步。**
2. **证据必须具体到函数名、库调用、写法特征。** 不能写"这段代码体现了深度学习能力"这类无法证伪的空话。
3. **未发现证据就明说"未发现证据"**，不要略过也不要猜。

## 写入规则

反推结果**绝不直接入库**。必须走确认流程：

1. 先展示上面的结构化结果
2. 再给一份**待写入草案**表格：

| 操作 | 知识点 | 状态 | 依据 | 置信度 | 建议 |
|---|---|---|---|---|---|
| 新增 | 图文匹配（CLIP） | 已掌握 | MNIST 项目里的向量相似度代码 | 0.72 | ✓ |
| 更新 | 线性代数 / 矩阵运算 | 在学 | 项目里出现矩阵乘法 | 0.55 | 建议你确认 |

3. **置信度 ≥ 0.7 的项建议勾选，低于 0.6 的留空并提示"建议你确认"**
4. 用户确认后才写入 `nodes` 与 `evidence` 表

## 禁止

- ❌ 用领域常识代替代码证据（**最常见也最致命的错误**）
- ❌ 输出"体现了 XX 能力"这类无法证伪的表述
- ❌ 在没有代码的情况下凭用户一句话下结论
- ❌ 把置信度低的推断当事实陈述
- ❌ 一次输出超过 6 条（宁可少而准）
- ❌ 直接写库不确认
