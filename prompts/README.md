# prompts/ —— 提示词单一事实来源

## 目录结构（v2，路由改由模型自己决定后）

```
prompts/
├── system.md            ← ★ 唯一的「正文」文件，逐字进入 worker.js
├── chat.md              ← 能力一的规格与设计说明（不是正文）
├── analyze-project.md   ← 能力二的规格与设计说明（不是正文）
└── plan-skeleton.md     ← 能力三的规格与设计说明（不是正文）
```

**只有 `system.md` 是待复制的正文。** 另外三份解释"为什么这么写"、记录调优方向，改提示词时读它们，但**不要把内容抄回来**——那样就会有两份正文，必然漂移。

## 为什么合并成一份

v1 用的是 `mode: 'chat' | 'analyze' | 'plan'` 三段独立提示词，让用户在界面上选模式。

**这条路走不通**，v1 的用户反馈里暴露了三个问题：

1. 用户不知道自己该点哪个按钮——"我就是想让 AI 帮我看看该学什么"，这既像能力反推又像路线规划。
2. 模型会向用户交代自己用了哪个模式（"你这句属于学习路径规划，我继续"），这类内部实现泄漏到对话里非常烦人。
3. 一次回答本来可以同时用多种能力（先反推能力，再据此排路线），分段锁死后做不到。

所以 v2 改成：**一份统一提示词，路由由模型自己判断。** 前端不再有模式按钮。

这也让两个交付形态的架构一致了——专家智能体本来就是模型按 SKILL.md 的 `description` 自己决定调哪个技能。

## 映射表

| 能力 | `system.md` 中的章节 | 专家包里的对应 skill | 触发描述在哪 |
|---|---|---|---|
| 方向收敛 | 能力一 | `domain-converge` | 该 SKILL.md 的 frontmatter |
| 能力反推 | 能力二 | `analyze-project` | 该 SKILL.md 的 frontmatter |
| 学习路线 | 能力三 | `plan-skeleton` | 该 SKILL.md 的 frontmatter |

**触发描述仍然只写在专家包里**，不进 `system.md`：Web 版没有"什么时候启动技能"这个问题（提示词永远全部在场），只有专家版需要。

## 两个交付形态怎么用它

| 交付物 | 位置 | 怎么用它 |
|---|---|---|
| 公网可对话页面 | `web-demo/worker.js` → `SYSTEM_PROMPT` | `system.md` 的正文原样粘贴 |
| LearnBuddy 专家智能体 | `expert/academic-nav/` → `agents/*.md` + `skills/*/SKILL.md` | 能力定义相同，但不含「前端渲染契约」一节 |

## 修改流程

1. 改 `system.md` 里 `<!-- PROMPT:BEGIN -->` 与 `<!-- PROMPT:END -->` 之间的正文
2. 原样贴进 `web-demo/worker.js` 的 `SYSTEM_PROMPT`
3. **跑校验**：

   ```bash
   node web-demo/scripts/check-prompts.mjs
   ```

   它会逐字比对两份文本，不一致直接报错——**这一步把"两边保持同一份"从口头纪律变成了机器检查。**
4. 涉及能力定义的改动，同步到专家包的 `agents/` 或 `skills/`，再跑 `node expert/sync.mjs`
5. 改提示词属于实质性变更，提交信息写清楚改了什么、为什么改

## 编写约定

1. **正文里不要出现反引号。** 它会截断 `worker.js` 的模板字符串。结构化块用 `[[PLAN]]` 这种自定义标记，不用 Markdown 代码块。
2. **正文里不要出现 `${`。** 同样是模板字符串的语法冲突。
3. **输出格式必须写死。** 越具体的格式约束，模型越不容易跑偏。
4. **必须写清"什么时候不该用"。** 这是防止模型强行套用的关键。
5. **禁止编造事实**（论文标题、作者、链接）要显式写进规则。
6. **要求模型暴露不确定性。** 低置信度的项要单独列出让用户确认，而不是混在一起下结论。
7. **不要给输出定字数上限。** v1 写过"400 字以内"，结果模型遇到"详细讲讲"就开始跟用户解释冲突并自我截断。长度应由内容决定。
