# plan-skeleton —— 能力三 · 学习路线

> **对应 skill**：`plan-skeleton`
> **正文位置**：`prompts/system.md` → 「能力三 · 学习路线」
> 本文件**不是待复制的正文**，而是这段能力的规格与设计说明。改提示词请改 `system.md`。

---

## 什么时候用

用户要计划、路线、排期、"我该学什么""先学什么"，或给出了目标与期限。

## 输入

- 目标领域
- 用户已掌握的知识点（可能为空）
- 起止日期与每周可投入时长

**信息不足先问齐**：目标领域、期限、每周或每天能投入多少小时。缺哪项问哪项，一次问完，不要替用户假设数值。

## 输出：必须分两段走

### 第一段 · 骨架（不给逐日内容）

```
## 计划目标
## 缺口分析        （按重要性排序，标注五个一级分类中的一个）
## 阶段安排        （起止日期 + 这一阶段解决什么 + 关键产出；最多 5 个阶段）
## 时间预算        （总可用 X 小时 / 各阶段分配 / 缓冲日放在哪）
## 明确不做        （这次不覆盖什么，以及为什么）
```

### 第二段 · 逐阶段展开到天

用户确认骨架后，一次只展开**一个**阶段，同时输出结构化路线块（见下）。

不要一次生成几十天——后半段质量会明显下滑，而且用户改一个阶段就得全部重来。

## 规则

1. 阶段按**前置依赖**排：后一个阶段必须真的需要前一个阶段的产出，不能只是主题相近。
2. 每个阶段必须有**可验证的产出标准**。写成"能独立完成 X 并解释 Y"才算合格，不能只写"学习 XX"。
3. 每 1–2 周安排一个**缓冲日**，不允许把时间排满。
4. 各阶段时间之和**不得超过**用户给出的可投入时间。超了要明说需要删掉什么。
5. 缺口大而时间紧时**直接说出来**，并建议缩小目标范围。
6. 必须写"这次不做的事"。**一份敢于说"不做什么"的计划，比什么都想覆盖的计划更可信。**
7. 每天必须给出 `outcome`（当天完成什么），且必须可验证——"能在简单情形套用两个不等式"，而不是"读 6.2 节"。
8. 计划形态按**缺口大小 + 用户意图**分，不按学历身份分。

| 形态 | 适用 | 知识线 : 论文线 |
|---|---|---|
| 基础型 | 前置缺口大，想系统补 | 80 : 20 |
| 混合型 | 有基础，想尽快上手 | 50 : 50 |
| 研究型 | 前置扎实，目标做研究 | 25 : 75 |

配比只是**建议起点**，明确告诉用户可以改。

## 前端渲染契约（**Web 版专属**）

展开到天时，在回答末尾追加一个结构化块，Web 页面据此渲染成可读的每日计划页面：

```
[[PLAN]]
{
  "goal": "一句话说清结束时用户能做什么，必须可验证",
  "form": "基础型 | 混合型 | 研究型",
  "startDate": "YYYY-MM-DD",
  "endDate": "YYYY-MM-DD",
  "hoursPerWeek": 10,
  "stages": [
    {
      "name": "阶段一 · 阶段名",
      "goal": "这个阶段结束时能做到什么",
      "startDate": "YYYY-MM-DD",
      "endDate": "YYYY-MM-DD",
      "items": [
        { "day": 1, "date": "YYYY-MM-DD", "outcome": "...", "reason": "...", "domain": "数学基础 › 线性代数", "minutes": 90 }
      ]
    }
  ]
}
[[/PLAN]]
```

字段说明：

| 字段 | 说明 |
|---|---|
| `day` | 整份计划的第几天，**全局连续编号**（不是阶段内序号）——分批展开时靠它拼成一份连续计划 |
| `date` | YYYY-MM-DD，与 `startDate` 推算一致 |
| `domain` | 以五个一级分类之一开头（数学基础 / 编程基础 / 理论基础 / 工具基础 / 科研素养），可用 › 接更细的层 |
| `minutes` | 当天预计投入分钟数 |
| `stages` | 一次只展开一个阶段，所以通常只有一个元素；前端按阶段名合并进已有计划 |

JSON 必须合法：双引号、无注释、无尾逗号。`[[PLAN]]` 块之外的正文照常写——用几句话说明这份路线怎么用、哪里最容易卡住，**不要用正文把 JSON 里的内容复述一遍**。

> **专家智能体版不需要这个块。** 专家版把计划写进资料库的 `plans` / `plan_stages` / `plan_items` 三张表，
> 页面渲染由资料库的「在线 page」能力负责。这个契约是给自建 Web 页面用的。

## 设计理由

| 设计 | 为什么 |
|---|---|
| 两段式（先骨架后展开） | 一次性排几十天，后半段质量会塌，且改一处就要全部重来 |
| `outcome` 必填且要可验证 | "读 6.2 节"是过程，"能套用不等式"是结果。只有结果能被检验，计划才可执行 |
| 必须写"明确不做" | 计划的边界比内容更能体现判断力 |
| 缓冲日强制留 | 排满的计划一定完不成，然后用户会放弃整份计划 |
| 按缺口分形态而非按身份 | 一个基础扎实的本科生可以直接读论文，一个跨专业的博士生可能需要补数学 |
| 全局连续 `day` | 逐阶段展开是分批的，只有全局编号才能拼成连续计划 |
