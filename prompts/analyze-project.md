# analyze-project —— 能力二 · 从项目代码反推能力

> **对应 skill**：`analyze-project`
> **正文位置**：`prompts/system.md` → 「能力二 · 能力反推」
> 本文件**不是待复制的正文**，而是这段能力的规格与设计说明。改提示词请改 `system.md`。
> **这是本作品最核心的一段提示词，也是技术创新性得分的主要来源。**

---

## 什么时候用

用户粘贴了项目代码、代码片段、文件树、`requirements.txt`、仓库链接，或说"我做过 X，帮我看看我会什么"。

用户只描述项目、没给代码时：先向他要代码并给出最小示例，**不要凭描述下结论**。

## 输出格式（固定，不得增删章节）

## 反推结果

**1. 知识点名称**
- 证据：引用代码里具体的位置或写法
- 推断：说明他掌握了什么
- 置信度：0.XX

**2. 知识点名称**
（同上结构，最多 8 条，按置信度从高到低）

## 需要确认

- 列出置信度低于 0.6 的项，逐条说明为什么不确定

## 三条铁律

1. **只依据代码里真实存在的证据。** 不能因为"做图像分类一般会用到 CNN"就推断他会 CNN。
2. 证据必须具体到函数名、库调用、写法特征，不能写"这段代码体现了深度学习能力"这类空话。
3. 没有发现证据的方面，明确写"未发现证据"，不要略过也不要猜。

置信度三档：0.9 以上＝有明确直接证据；0.6–0.9＝有较强特征但可能来自教程模板；0.6 以下＝弱信号。

## 设计理由（改动时不要丢掉）

| 设计 | 为什么 |
|---|---|
| 强制三行结构（证据 / 推断 / 置信度） | 让结论可追溯。用户和评委都能看到"AI 凭什么这么说" |
| "不能因为…就推断…" | 这是模型最容易犯的错：用领域常识代替代码证据。**这条删掉，整个功能就退化成算命** |
| 证据必须具体到函数名 | 防止输出"体现了深度学习能力"这类无法证伪的空话 |
| 置信度三档明确定义 | 模型对置信度没有先验，不给标准就会全给 0.8 |
| 低置信度项单独列出 | 把不确定性显式暴露给用户，而不是混在一起给结论。**这是本产品最容易被记住的一处细节** |
| 没给代码就先要代码 | 早期版本里模型会凭项目名开始编能力清单，这一条是补丁 |

## 实测案例（线上验证过）

输入一段 MNIST 训练脚本，模型的输出包括：

> **GPU 训练（CUDA）** — 证据：`model = Net().cuda()` — 置信度 0.75
> **需要确认**：仅有 `.cuda()` 调用，**未出现数据迁移到 GPU 的写法**。若数据仍在 CPU 上，这段代码实际会报错…

它抓到了"`.cuda()` 没配数据迁移"这个细节，并因此下调置信度——这正是本功能要达到的效果。**这段案例适合放进 PPT。**

## 调优方向

- [ ] **按文件类型分流**：`requirements.txt` 主要看工具链，训练脚本主要看算法，目录结构主要看工程规模。目前是一套提示词吃所有输入。
- [ ] **收紧"抄来的代码"判定**：出现大量教程式完整范例（如 MNIST 的标准写法）时，应主动降低置信度并提示"这段代码可能来自教程"。
- [ ] **加追问环节**：置信度低于 0.6 的项，主动提一个具体问题请用户确认，而不是只在末尾列出来。
